# `tools/bench` — the measurement instrument

Not in `Gg2.sln`. Build it explicitly; `dotnet test` should not build a benchmark
and CI should not run one.

```powershell
$env:PATH = "$env:LOCALAPPDATA\Microsoft\dotnet;$env:PATH"
$env:DOTNET_ROOT = "$env:LOCALAPPDATA\Microsoft\dotnet"
dotnet publish -c Release tools/bench/bench.csproj -o <somewhere>
```

**Publish to a fresh directory, not over a running one.** A background
`bench.exe` holds its own file, `dotnet build` then silently cannot overwrite it,
and the next run measures the *old* binary. That cost a session an hour and looks
exactly like a change having no effect.

Every mode is selected by an environment variable and configured by more of them.
There is no argument parser; `Program.cs` is a chain of
`if (GetEnvironmentVariable(...) is { } x)`.

Common to most modes:

| variable | meaning |
|---|---|
| `GG2_REFERENCE` | the reference checkout (default `D:\code\Gang-Garrison-2` — stock GG2 v2.9.2) |
| `GG2_NAV` | the bot nav cache directory — normally `<repo>/nav`. Not the same name as the test suite's `GG2_NAVCACHE`, and required here rather than defaulted |
| `NPZ` | a `gg2-rl` policy checkpoint |
| `BENCH_MAP`, `BENCH_FOCUS` | which map, or a comma-separated list |

## Read this before adding a mode or reading a number

The whole reason this exists in the repo rather than in a scratch directory is
the set of measurement traps in `docs/BOTS.md`, "Measuring a bot change". Nine
are built into the code here.

**Traps 1, 5 and 7 are one rule wearing three coats: keep a qualifier
attached to the thing it qualifies, because anything separable by a
copy-paste or a scroll gets separated.** A subset size belongs in the row, not
the caption; a constant's provenance belongs in the comment beside it, not at
the top of the file; a verdict's scope belongs in the same block, not forty
lines below it.

1. **A statistic over a subset prints the subset size in the same row.** Never
   in a caption — a caption can be separated from the number by a copy-paste.
2. **`decided` is not the win share's denominator.** `MatchOutcome.Decided`
   includes a draw. Wins-plus-losses is the denominator, and on some maps it
   is a twentieth of the decided count.
3. **Warm past tier-1 before measuring.** Promotion is at 30 calls and the
   rejit is asynchronous, so a short warm-up measures tier-0 code. Modes here
   warm with 200,000 iterations.
4. **Keep the control arm even when it looks redundant.** A control row added
   only to validate an assumption is where real findings turn up.
5. **A duel is not a small match — it is a match with POPULATION SET TO 2.**
   A rollout re-simulates every live character for every tick of every
   candidate, so a decision costs **2.47 ms at two characters and 7.64 ms at
   twelve**. `BENCH_POP` exists because that term is invisible at the
   default: it never reads as an approximation, it reads as a number with no
   population in it. **Anything measured in a two-character scenario and
   quoted into a twelve-bot match is wrong by 3x.**
6. **Before quoting a per-unit average, ask what the units SHARE.** If they
   share a resource with a deadline, the mean is not the constraint and the
   tail is. Twelve bots searching at 7% duty is 4.9% of a core — correct, and
   useless: the server is single-threaded at 30 Hz, one decision is **23% of
   a tick**, and handovers are correlated because several bots have an enemy
   in range during the same firefight. **The mean is an average over a
   distribution whose tail is generated by the event the thing exists for.**
   **And once you are measuring a MAXIMUM, the question stops being `n` and
   becomes COVERAGE.** A max is monotone in coverage — adding units can only
   raise it — so a max over a subset is a **lower bound** on the whole:

       subset EXCEEDS the budget  ->  conclusive; the whole does too
       subset is UNDER the budget ->  no evidence at all

   **"It passed on these three maps" is therefore not weak evidence of a
   pass, it is NOT evidence of a pass** — while a fail on three would have
   settled it outright. **The same subset carries a conclusive verdict one
   way and none the other.** A three-map max under budget is not license to
   call something shippable; check the full map set before publishing a
   ship/no-ship number.
7. **Every constant in a printed expression carries its date and the mode
   that produced it, in the comment beside it.** A bare literal in an
   expression is indistinguishable from a measurement at the call site — no
   citation, no date, nothing to prompt the lookup — so the plausible reading
   is the one that stops anybody checking.
8. **The first timing in a process is not a timing, and trap 3 does not
   cover this.** A serial/baseline rung that runs first pays the JIT for the
   simulation, the bot layer and the collision world, and every later rung is
   warm — producing speedup ratios that look plausible (or, if arithmetically
   impossible, at least catch attention) but are wrong either way. Trap 3
   warms the code a mode measures; a mode whose first row is the baseline for
   later rows needs the warm-up to precede the *comparison*, not the call —
   build every rung first, then run them round-robin. A mode that compares
   arms within a row is not exposed to this. **Re-measure before repeating
   any factor out of `BENCH_THREADS`** — it is a wall-clock ratio on this
   machine and is not portable to another one.
9. **The first SECONDS of a bench process on this box run 5-30x slow, and
   trap 3 and trap 8 both miss it.** A settled twelve-bot match is ~12 µs a
   tick; the first ~15,000 ticks read 50-260, reproducibly, with every region
   scaling together and the A\* call count unchanged — a clock or scheduler
   ramp, not a code path and not the JIT. Trap 3 warms by iteration count and
   trap 8 warms the first row of a ladder; this outlasts both by an order of
   magnitude in wall clock, and a mode that warms by ticks reports the ramp
   as its measurement. `BENCH_COMBAT` warms with a **stability test on wall
   time** and prints `settled=`. The mean across runs is also a measure of
   what else was on the machine. **Quote the minimum, and repeat the run when
   min and median disagree by more than a few percent.**

## Modes that matter for bot work

| variable | what it does |
|---|---|
| `BENCH_PERMAP=<n>` | **the criterion.** Every shipped map, `n` matches an arm, policy against an all-scripted control. Prints absolute win and death counts, a two-proportion z per comparison, and `capped`. `BENCH_CAP=<minutes>` sets the match cap. |
| `BENCH_SWEEP=<n>` | **the mechanism.** Control plus policy at each engagement range in `BENCH_RANGES`. Prints the policy's share of control, both death-share estimators, the zero-death count, why each match ended, and — at `BENCH_CAP > 5` — the matches stratified by the 300-second boundary. |
| `BENCH_ARMS=<n>` | **arm 3.** Every shipped map, `n` matches an arm, THREE arms: all-scripted, policy hybrid, search hybrid. Prints death share per arm, each hybrid’s control share, and **max tick time per arm as a co-primary GATE** — an arm over 33.3 ms is unshippable whatever its death share, and the death-share criterion cannot see it. `BENCH_BOTS=<n>` sets the bot count: **8 keeps the death share comparable to phase 4; 12 is the shipping configuration and the one whose tick tail matters.** Run both and say which each number came from. |
| `BENCH_COMBAT=<n>` | **what a twelve-bot match costs, and how many A\* searches it buys.** `n` whole matches on `BENCH_MAP`, after a warm-up that runs matches until three consecutive ones agree within 8%. Prints min/med/max µs a tick, `searches`/1000 ticks and `goals`/1000 ticks — the second being `BotPathState.GoalsSet`, the half of the search budget the objective layer owns (**181 of 321** on `ctf_truefort`). **Read the minimum, not the mean**, and **a run printing `settled=False` measured the ramp** — see the file's own remarks and trap 9. |
| `BENCH_NAVDIST=1` | with `BENCH_COMBAT`, runs the same match with A*'s heuristic replaced by the exact precomputed one (`--nav-distances`). **A different ARM, not a faster run of the same one** — the search is weighted, so the routes differ and the search COUNT differs with them (320.0 -> 271.7 per 1000 ticks on `ctf_truefort`). The two columns are comparable in tick cost and in nothing else; `docs/TRAPS-BOTS.md`, "Shipping the precomputed distances". |
| `BENCH_CONST=1` | prints `SimulationStamp.Uuid`, `ObservationWriter.Length`, `ActionDecoder.AimBins` and the encoding version. **This is how you read the digest** when a stamp bump lands and `gg2-rl` needs to know whether its checkpoints survive — cheaper and less error-prone than running the test that pins it. |
| `BENCH_POLICYCOST=1` | one forward pass and one observation extraction, in nanoseconds. `OBS` points at an observations fixture. |
| `BENCH_SEARCH=1` | a `RolloutSearch` decision's cost, split into the per-candidate fork and the per-candidate tick by sweeping the horizon. **`BENCH_POP=<n>` sets how many characters are ALIVE** and defaults to 2 — see trap 6. `BENCH_CLASS=sniper` measures the 120-candidate set; `BENCH_CADENCE` sets the continuation cadence. |
| `BENCH_EVAL=<n>` | the handover-rule and engagement-range comparison that chose the 150px default. |
| `BENCH_SEARCHCLASSES=<n>` | **does the search still help on classes outside the policy's trained set.** Every shipped map, `n` matches an arm, two arms populated from `BENCH_CLASSES` (default `Pyro,Medic,Engineer,Spy,Sniper`): all-scripted, and the search hybrid with `RestrictToTrainedClasses` OFF, red the hybrid team. Prints wins and death share per map, the pooled aggregate with a two-proportion z, and **death share by the victim's class**, because a pooled share can hide one class losing inside four that win and death share alone would pass a medic that stopped healing. No arbiter, as `BENCH_ARMS` arm 3, so its max tick is that arm's ceiling rather than the live server's. `BENCH_SEARCHCLASSES_CSV=<path>` writes one row per match with per-class deaths. **Run it on `BENCH_CLASSES=Scout,Soldier,Demoman,Heavy` as the control**: that is the set every earlier search number came from, so the known result has to reappear there before the new classes' numbers mean anything. |
| `BENCH_SEARCHCLASSES_CSV=<path>` | with `BENCH_SEARCHCLASSES`, one row per match. |
| `BENCH_CLASSES=<a,b,c>` | with `BENCH_SEARCHCLASSES`, the roster both arms and both teams are populated from. |
| `BENCH_CHURN=<n>` | **is the bot the stutter.** How often each bot CHANGES its input, per bot-second, for all three arms: horizontal changes, reversals, **airborne reversals** and aim changes. Input churn is a netcode quantity — clients dead-reckon each character from the last keys they heard until the next position update (every 7th tick), so ~4.3 gaps a second, and a reversal inside a gap is a visible correction. **A low number does NOT clear the bots**, it moves the question to whether client and server agree on the physics, which this cannot see. `NPZ` points at the checkpoint, loaded with the stamp check bypassed so it measures what the live server runs. |
| `BENCH_THREADS=<n>` | **can arm 3 be made affordable.** Arm 3 ONLY, `n` matches a map, replayed at each thread count in `BENCH_THREAD_LADDER` (default `1,2,4,8`) — the same seeds, so every rung plays the identical match and the tick columns are paired. Prints max and mean tick per rung, the speedup on each, and the tick gate at the top rung. **The serial column is only the arm-3 baseline at the SAME `BENCH_BOTS`, `BENCH_CAP` and match count** — a max is monotone in coverage, so a cheaper run reproduces a smaller number and flatters nothing but itself. |
| `BENCH_THREAD_LADDER=<a,b,c>` | the thread counts `BENCH_THREADS` walks. **The last rung is the one the gate is read at**, and the speedup columns are all relative to the first. |
| `BENCH_ARMS_CSV=<path>` | with `BENCH_ARMS`, writes **one row per MATCH** — map, arm, index, red and blue deaths, ticks, max tick. **Record the unit of observation, not just the total**: the totals lose the unit, and this bench twice needed a full 21-map re-run because a later question wanted deaths per match rather than deaths per map. |
| `BENCH_SMOKE=1` | **does every checkpoint-driven mode still RUN.** All six at one match on one map, each caught separately so a broken one does not hide the rest, exit 1 if any threw. **Not a measurement** — the numbers are meaningless at that size and the exit status is the whole output. Run it after touching this directory. **It proves almost nothing against a `combat4`-family checkpoint**, whose set IS `DefaultTrainedClasses`: the three faults of 2026-09-06 are all invisible when the constant and the file agree, so it warns loudly and you should hand it `tests/Gg2.Tests/Fixtures/policy/rest3_s1_iter12000.npz` (`ENGINEER,SPY,PYRO`). **Deliberately not in `Gg2.sln` and not in CI** — `CLAUDE.md`'s rule stands; this is the cheap way to obey it, which is what was missing. Verified it fires: re-introducing the `995cef6` null dereference fails `BENCH_PERMAP` and only it.
| `BENCH_FLIGHT=1` | **is the nav graph followable at all.** Every edge of every graph in `GG2_NAV`, flown as a single hop by a real bot under the real follower, with the next-hop tables ON. Prints a per-map row, a per-edge-kind row and the corpus tally. **`measured` is the denominator and it is 28% of `candidates`** — A\* prefers to route around 72,926 of the 116,316 edges, so those cannot be posed as a one-hop question at all. **A sweep of every edge is not a check of every edge**; `BENCH_FLIGHT_ROUTES` is the complement. `stranded` is relative to `BENCH_FLIGHT_BUDGET`: 703 at 400 ticks, 453 at 1,600, **429 at 4,000** — and blacklist fires go 5,140 → 76,177 → 297,166 the other way, so the budget that measures followability is not the one that measures cost. An edge whose from-node sits in a team gate is flown by the team that can stand there (`team-swapped`, 178) — see `docs/TRAPS-BOTS.md`, "Two of the harness's own faults". |
| `BENCH_FLIGHT_ROUTES=<n>` | **can a bot get from anywhere to anywhere.** `n` random node pairs a map, planned and then flown end to end, covering edges in the context A\* actually uses them in — including every edge `BENCH_FLIGHT` skips. Prints arrival share, average hops and how many distinct node pairs the sample walked. **`noroute` is not a failure**: a graph describes the terrain, so it carries islands (96 of 200 pairs on `gg_debug`). A sample, not a census — all-pairs is 6.5M routes, about five core-hours. |
| `BENCH_FLIGHT_ORACLE=<n>` | **is a stranded arc the follower's fault or the generator's?** Two instruments over the same two arms — every stranded arc, and `n` arcs the follower demonstrably **flew** (not merely arrived at; the control must exclude the diverted arrivals). **A rate is only readable next to that arm's recall**, which is why both are printed in one block. Measured 2026-09-06: the open-loop input search finds **22.4%** of stranded arcs flyable at **33.5% recall** — its negatives are noise. The **real follower put on the takeoff column** finds **32.2%** at **88.5% recall**, so about a third of strandings are the APPROACH rather than the arc, and its negatives do carry information. `docs/TRAPS-BOTS.md`, "Attributing the 429". With `BENCH_FLIGHT_CSV` it also writes one row per stranded arc with `approach=1` where the arc is fine and only the approach failed — the 109 whose takeoff-speed window turns out to be narrow. |
| `BENCH_FLIGHT_LAUNCH=<n>` | **what a rocket-jump takeoff actually DELIVERS**, against what the arc was costed to need. Rocket arcs only; the same two arms as `BENCH_FLIGHT_ORACLE` (every stranded arc, and `n` arcs the follower demonstrably flew). Per arc, best over the same six takeoff speeds: did the blast go off, the deepest launch `vspeed`, the rise and reach achieved against those needed, whether the body ever resolved to the to-node, its closest approach to the goal, and whether one attempt both arrived and steered the edge. **It exists because the oracle's negative half was unreadable** — "this follower cannot fly it from a perfect start" does not say which of blast, height or reach was missing, and measured 2026-09-06 the answer is **none of them**: the launch is −14.40 in BOTH arms, and 87.8% of stranded rocket arcs put the body inside the destination. `docs/TRAPS-BOTS.md`, "What a rocket jump delivers". With `BENCH_FLIGHT_CSV` it writes one row per arc in both arms, including the arrival band (`bandticks`, `bandmin`) — the arrival test's own clause, which is where the 8 overshoot arcs are.
| `BENCH_FLIGHT_TRACE=<map>:<area>:<edge>` | **one arc, one tick a line**, from the takeoff column at each of the six swept speeds — x, y, both speeds, on-ground, `moveStatus`, air ticks, the hop the follower is steering, the node under the body, hops left, and where off-route and blacklist fired; then the gate counters. Consecutive identical lines are collapsed, because a bot standing at a gate for eighty ticks is one fact. **The instrument of last resort, and it earned its place**: the aggregates said the failures and the successes were indistinguishable in blast, height and reach, which names no mechanism — one trace found the cold launcher in a minute. `BENCH_FLIGHT_BUDGET` caps the ticks printed.
| `BENCH_FLIGHT_WARM=1` | places every flight's bot with its weapon **already off cooldown**. **A different ARM, and it exists as a control rather than as a better number.** `ScenarioWorld.Place` spawns a character, and `Weapon.events/Create.xml` starts a fresh weapon with `ReadyToShoot` false and the refire alarm running, so every rocket-jump flight begins ~45 ticks from being able to fire — which a bot that has been alive in a match for any time is not. **It is what found the routing bug and it is what bounds the residual**: before `RocketModel.Capable`, warming took stranded 622 → 520 and `diverted` 2,128 → 48; after the fix the shipping (cold) arm is 536/33 and warming buys only 536 → 508. `docs/TRAPS-BOTS.md`, "A cold launcher unplanned the route".
| `BENCH_FLIGHT_BUDGET=<n>` | ticks a flight gets before it counts as stranded. Default 400 for `BENCH_FLIGHT`, 3000 for `BENCH_FLIGHT_ROUTES`. **Half of a stranding count** — the two are quoted together or neither is quoted. |
| `BENCH_FLIGHT_NODIST=1` | plans without the next-hop tables. **A different ARM, not a faster run** — the search is weighted, so it changes which hops are posable: `measured` goes 32,055 → 37,787 and measurable rocket jumps 3,536 → 5,658. The two tallies are not comparable as runs of one thing. |
| `BENCH_FLIGHT_THREADS=<n>` | flights at once; 0 (the default) is one per core. Named apart from `BENCH_THREADS`, which selects a different mode entirely. The result does not depend on it — `EdgeFlightTests.TheSweepIsTheSameHoweverManyThreads`. |
| `BENCH_FLIGHT_CSV=<path>` | with `BENCH_FLIGHT`, writes **one row per MEASURED edge** — map, area, edge index, kind, from, to, outcome, team, swapped, ticks, manoeuvres, blacklists, miss. **The arrivals are the control and are written too**: a claim about the failures ("these arcs demand more takeoff speed than the node affords") is not checkable without them, and filtering to the strandings is one `awk` where recovering the control is a re-run. **Record the unit of observation**: the tally says 703 edges failed and cannot say which. `cp_dirtbowl` holds 131 of the 429 that survive a 4,000-tick budget. |
| `BENCH_FLIGHT_SEED=<n>` | the route sample's seed. Hashed per map so one map reproduces without running the ones before it. |
| `clustered.py <csv>` | **the match-level death-share test.** A death is not an independent observation — ~40 arrive together per match — so a pooled test over ~34,000 deaths overstates its own evidence. This makes each MATCH one observation and compares arms with Welch t, sidestepping clustering rather than correcting for a correlation nobody can estimate. Prints the zero-death drop rate **per arm**, because what invalidates a comparison is a filter that DIFFERS between arms. |
| `stability.py <small> <large>` | **does a per-map death-share DIRECTION survive the sample size?** Two `BENCH_PERMAP` tables at different match counts. **Prints the smallest effect at which every direction held, and says to quote THAT rather than the agreement count** — direction stability is a property of effect size relative to noise, not of `n`, so "21 of 21 agreed" goes wrong the moment somebody applies it to a one-point effect. |
| `analyse.py <table>` | reads a `BENCH_PERMAP` table and prints what it cannot show by eye: the decisive denominator per map, a filter-equality z, the maps ranked by **differential** censoring, and the death-share signs counted mechanically. |

**`analyse.py` ranks on `decisive`, not on `decided`, and prints the `decided`
ranking underneath to show they disagree.** Ranking on `decided` sees the time-cap
layer and is blind to the draw layer — it clears a map whose two arms are 6%
decisive and flags one that is fine.

## Modes kept for reference, not current

These answered one question each and are unlikely to be run again. They are here
because they were never in git and would otherwise be lost, not because they are
maintained.

`BENCH_ALLOC` `BENCH_CMP` `BENCH_COLD` `BENCH_DIGEST` `BENCH_DUEL` `BENCH_GEOM`
`BENCH_LAT` `BENCH_OBS` `BENCH_RAY` `BENCH_RESET`
`BENCH_TICK` — the `Gg2.Env` throughput and allocation work
(`docs/BOTS.md`, "The environment seam"). `BENCH_LAT` takes `BENCH_NODELAY` and
`BENCH_BUFFERED` to vary the socket. `BENCH_DKOTH` verified one bug
fix and is superseded by `BENCH_PERMAP`, which also takes `BENCH_CONFIRM` to
re-run a cell.

**Document a mode under the variable you TYPE, not the class that
implements it** — a mode documented under a name that cannot be typed is
undocumented. `BenchModeCoverageTests` checks this table against `Program.cs`
mechanically.

**A number from one of these is older than the code.** Re-run before
quoting.
