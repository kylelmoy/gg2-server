# `tools/bench` — the measurement instrument

Not in `Gg2.sln`. Build it explicitly; `dotnet test` should not build a benchmark
and CI should not run one.

```powershell
$env:PATH = "$env:LOCALAPPDATA\Microsoft\dotnet;$env:PATH"
$env:DOTNET_ROOT = "$env:LOCALAPPDATA\Microsoft\dotnet"
dotnet publish -c Release tools/bench/bench.csproj -o <somewhere>
```

⚠️ **Publish to a fresh directory, not over a running one.** A background
`bench.exe` holds its own file, `dotnet build` then silently cannot overwrite it,
and the next run measures the *old* binary. That cost a session an hour and looks
exactly like a change having no effect.

Every mode is selected by an environment variable and configured by more of them.
There is no argument parser; `Program.cs` is a chain of
`if (GetEnvironmentVariable(...) is { } x)`.

Common to most modes:

| variable | meaning |
|---|---|
| `GG2_REFERENCE` | the reference checkout (default `D:\code\Gang-Garrison-2-upstream` — stock GG2, **not** the bot fork) |
| `GG2_NAV` | the bot nav cache directory — normally `<repo>/nav`. ⚠️ Not the same name as the test suite's `GG2_NAVCACHE`, and required here rather than defaulted |
| `NPZ` | a `gg2-rl` policy checkpoint |
| `BENCH_MAP`, `BENCH_FOCUS` | which map, or a comma-separated list |

## ⛔ Read this before adding a mode or reading a number

The whole reason this exists in the repo rather than in a scratch directory is
the set of measurement traps in `docs/BOTS.md`, "Measuring a bot change". The
eight built into the code here.

⛔ **Traps 1, 5 and 7 are ONE rule wearing three coats, and naming it stops this
list growing an entry per instance: remove the separation that lets a qualifier be
dropped.** A subset size in the row rather than the caption; a constant’s
provenance in the comment beside it rather than at the top of the file; a
verdict’s scope in the same block rather than forty lines below it. **A qualifier
is only as durable as the thing it is attached to** — anything separable by a
copy-paste or a scroll gets separated. It is the measurement-shaped half of
`gg2-rl`’s *make the mistake unavailable*, which does the same job for a value, a
guard site and a method signature.

1. **A statistic over a subset prints the subset size in the same row.** Never in
   a caption — a caption can be separated from the number by a copy-paste.
2. **`decided` is not the win share's denominator.** `MatchOutcome.Decided`
   includes a draw. Wins-plus-losses is the denominator, and on some maps it is a
   twentieth of the decided count.
3. **Warm past tier-1 before measuring.** Promotion is at 30 calls and the rejit
   is asynchronous, so a short warm-up measures tier-0 code. Modes here warm with
   200,000 iterations.
4. **Keep the control arm even when it looks redundant.** Two of the biggest
   findings of 2026-09-01 came out of a control row added only to validate an
   assumption.
5. ⛔ **A duel is not a small match — it is a match with POPULATION SET TO 2.** A
   rollout re-simulates every live character for every tick of every candidate, so
   a decision costs **2.47 ms at two characters and 7.64 ms at twelve**. `BENCH_POP`
   exists because that term is invisible at the default: it never reads as an
   approximation, it reads as a number with no population in it. ⚠️ **Anything
   measured in a two-character scenario and quoted into a twelve-bot match is
   wrong by 3x**, and this seam has now produced that error three times on three
   different quantities — a handover radius, a search cost and a duty cycle.
6. ⛔ **Before quoting a per-unit average, ask what the units SHARE.** If they
   share a resource with a deadline, the mean is not the constraint and the tail
   is. Twelve bots searching at 7% duty is 4.9% of a core — correct, and useless:
   the server is single-threaded at 30 Hz, one decision is **23% of a tick**, and
   handovers are correlated because several bots have an enemy in range during the
   same firefight. **The mean is an average over a distribution whose tail is
   generated by the event the thing exists for.**
   ⛔ **And once you are measuring a MAXIMUM, the question stops being `n` and
   becomes COVERAGE.** A max is monotone in coverage — adding units can only
   raise it — so a max over a subset is a **lower bound** on the whole:

       subset EXCEEDS the budget  ->  conclusive; the whole does too
       subset is UNDER the budget ->  no evidence at all

   ⚠️ **"It passed on these three maps" is therefore not weak evidence of a pass,
   it is NOT evidence of a pass** — while a fail on three would have settled it
   outright. **The same subset carries a conclusive verdict one way and none the
   other.** This repo published "shippable at 8 bots" off a three-map max that was
   under budget; the 21-map run failed on 20 of 21 at the same bot count. ⚠️ The
   sample-size question was asked and correctly answered — *n cannot weaken a
   maximum* — and **being right about that axis is what stopped anybody asking
   about the other one.** `gg2-rl`, 2026-09-01.
7. ⛔ **Every constant in a printed expression carries its date and the mode that
   produced it, in the comment beside it.** `Search.cs` held a bare `4.7` as the
   per-tick cost of a policy continuation. It was an estimate, it was 1.4x low,
   and it drove the `(affordable)`/`(OVER)` column that this repo *and* `gg2-rl`
   read for a day. **A bare literal in an expression is indistinguishable from a
   measurement at the call site** — no citation, no date, nothing to prompt the
   lookup — so the plausible reading is the one that stops anybody checking. It
   survived in the file whose README you are reading, three lines under a warning
   that its numbers go stale. Found by trying to *compute* something with it, not
   by reading it.
8. ⛔ **The first timing in a process is not a timing, and trap 3 does not cover
   this.** `BENCH_THREADS` reported **11.81x on four threads** and **6.12x on the
   mean**. Both are arithmetically impossible, which is the only reason anybody
   looked: the serial rung ran first and paid the JIT for the simulation, the bot
   layer and the collision world, and every later rung was warm.
   ⚠️ **The impossible number is the LUCKY case.** The same defect on a two-rung
   ladder produces something near **1.9x on two threads** — exactly what a correct
   measurement looks like, and it would have been written down.
   ⚠️ **Trap 3 was already in this file and did not stop it.** Trap 3 warms the
   code a mode measures; this is a mode whose FIRST ROW is the baseline for the
   rows beneath it, so the warm-up has to precede the comparison rather than the
   call. Any mode that reads one row as a baseline for later rows is exposed; a
   mode that compares arms *within* a row is not.
   ⚠️ **Re-measure before repeating any factor out of this mode** — it is a
   wall-clock ratio on a 24-core machine, and it is not portable to another one.

## Modes that matter for bot work

| variable | what it does |
|---|---|
| `BENCH_PERMAP=<n>` | **the criterion.** Every shipped map, `n` matches an arm, policy against an all-scripted control. Prints absolute win and death counts, a two-proportion z per comparison, and `capped`. `BENCH_CAP=<minutes>` sets the match cap. |
| `BENCH_SWEEP=<n>` | **the mechanism.** Control plus policy at each engagement range in `BENCH_RANGES`. Prints the policy's share of control, both death-share estimators, the zero-death count, why each match ended, and — at `BENCH_CAP > 5` — the matches stratified by the 300-second boundary. |
| `BENCH_ARMS=<n>` | **arm 3.** Every shipped map, `n` matches an arm, THREE arms: all-scripted, policy hybrid, search hybrid. Prints death share per arm, each hybrid’s control share, and ⛔ **max tick time per arm as a co-primary GATE** — an arm over 33.3 ms is unshippable whatever its death share, and the death-share criterion cannot see it. `BENCH_BOTS=<n>` sets the bot count: ⚠️ **8 keeps the death share comparable to phase 4; 12 is the shipping configuration and the one whose tick tail matters.** Run both and say which each number came from. |
| `BENCH_CONST=1` | prints `SimulationStamp.Uuid`, `ObservationWriter.Length`, `ActionDecoder.AimBins` and the encoding version. ⚠️ **This is how you read the digest** when a stamp bump lands and `gg2-rl` needs to know whether its checkpoints survive — cheaper and less error-prone than running the test that pins it. |
| `BENCH_POLICYCOST=1` | one forward pass and one observation extraction, in nanoseconds. `OBS` points at an observations fixture. |
| `BENCH_SEARCH=1` | a `RolloutSearch` decision's cost, split into the per-candidate fork and the per-candidate tick by sweeping the horizon. ⚠️ **`BENCH_POP=<n>` sets how many characters are ALIVE** and defaults to 2 — see trap 6. `BENCH_CLASS=sniper` measures the 120-candidate set; `BENCH_CADENCE` sets the continuation cadence. |
| `BENCH_EVAL=<n>` | the handover-rule and engagement-range comparison that chose the 150px default. |
| `BENCH_THREADS=<n>` | **can arm 3 be made affordable.** Arm 3 ONLY, `n` matches a map, replayed at each thread count in `BENCH_THREAD_LADDER` (default `1,2,4,8`) — the same seeds, so every rung plays the identical match and the tick columns are paired. Prints max and mean tick per rung, the speedup on each, and the tick gate at the top rung. ⛔ **The serial column is only the arm-3 baseline at the SAME `BENCH_BOTS`, `BENCH_CAP` and match count** — a max is monotone in coverage, so a cheaper run reproduces a smaller number and flatters nothing but itself. |
| `BENCH_THREAD_LADDER=<a,b,c>` | the thread counts `BENCH_THREADS` walks. ⚠️ **The last rung is the one the gate is read at**, and the speedup columns are all relative to the first. |
| `BENCH_ARMS_CSV=<path>` | with `BENCH_ARMS`, writes **one row per MATCH** — map, arm, index, red and blue deaths, ticks, max tick. ⛔ **Record the unit of observation, not just the total**: the totals lose the unit, and this bench twice needed a full 21-map re-run because a later question wanted deaths per match rather than deaths per map. |
| `clustered.py <csv>` | ⛔ **the match-level death-share test.** A death is not an independent observation — ~40 arrive together per match — so a pooled test over ~34,000 deaths overstates its own evidence. This makes each MATCH one observation and compares arms with Welch t, sidestepping clustering rather than correcting for a correlation nobody can estimate. ⚠️ Prints the zero-death drop rate **per arm**, because what invalidates a comparison is a filter that DIFFERS between arms. |
| `stability.py <small> <large>` | ⛔ **does a per-map death-share DIRECTION survive the sample size?** Two `BENCH_PERMAP` tables at different match counts. ⚠️ **Prints the smallest effect at which every direction held, and says to quote THAT rather than the agreement count** — direction stability is a property of effect size relative to noise, not of `n`, so "21 of 21 agreed" goes wrong the moment somebody applies it to a one-point effect. |
| `analyse.py <table>` | reads a `BENCH_PERMAP` table and prints what it cannot show by eye: the decisive denominator per map, a filter-equality z, the maps ranked by **differential** censoring, and the death-share signs counted mechanically. |

⚠️ **`analyse.py` ranks on `decisive`, not on `decided`, and prints the `decided`
ranking underneath to show they disagree.** Ranking on `decided` sees the time-cap
layer and is blind to the draw layer — it clears a map whose two arms are 6%
decisive and flags one that is fine.

## Modes kept for reference, not current

These answered one question each and are unlikely to be run again. They are here
because they were never in git and would otherwise be lost, not because they are
maintained.

`BENCH_ALLOC` `BENCH_CMP` `BENCH_COLD` `BENCH_DIGEST` `BENCH_DUEL` `BENCH_GEOM`
`BENCH_LAT` `BENCH_OBS` `BENCH_RAY` `BENCH_RESET`
`BENCH_TICK` — the `Gg2.Env` throughput and allocation work
(`docs/BOTS.md`, "The environment seam"). `BENCH_LAT` takes `BENCH_NODELAY` and
`BENCH_BUFFERED` to vary the socket. `BENCH_DKOTH` verified one bug
fix and is superseded by `BENCH_PERMAP`, which also takes `BENCH_CONFIRM` to
re-run a cell.

⚠️ **Named by the variable you TYPE, not by the class that implements it.** This
list said `Alloc`, `Latency` and `Dkoth` until 2026-09-01, and the variables are
`BENCH_ALLOC`, `BENCH_LAT` and `BENCH_DKOTH` — two of the three not derivable
from the name given. **A mode documented under a name that cannot be typed is
undocumented**, which is what `BenchModeCoverageTests` now says mechanically.

⚠️ **A number from one of these is older than the code.** Re-run before quoting.

⚠️ **`Search` was on that list until 2026-09-01 while also being in the table
above** — a file calling the same mode current and superseded in two places, found
by auditing the modes against `Program.cs` rather than by reading. **`BENCH_CONST`
was in neither**, so a mode that prints the simulation digest existed and was
documented nowhere. ⛔ **Nothing checks this table against the code**, which is the
shape CLAUDE.md names: the instrument making a claim about itself that only a
reader who acts on it can falsify.
